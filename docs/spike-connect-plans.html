Spike Connect: roadmap, business and engineering plans

A privacy-first communication network for people, AI agents and devices. Launch with agent coordination and private messaging for Spike OS users and design partners; expand only when the gates pass.

Product roadmap

Spike Connect is the application and service. Spike Network is the interoperable infrastructure underneath it.

Pillars

Connect Chat

Direct messages, groups, attachments, presence. Read receipts are opt-in.

Connect Agents

Agent identity, discovery, permission scopes, approval flows, signed requests and receipts.

Connect Link

Trusted device pairing, file transfer and sync.

Connect Network

Identity, encrypted transport, routing, relays, push and delivery queues.

Connect Admin

Org provisioning, policies, retention and observability without content access.

First-pilot scope PAPER

Include

  • Desktop-to-desktop chat
  • Identity and device pairing
  • E2EE one-to-one, encrypted local history
  • Relay fallback and offline queue
  • Agent messages with explicit approval
  • Basic attachments and diagnostics

Defer

  • Public discovery and large communities
  • Custom cryptographic primitives
  • Video calling and livestreaming
  • Autonomous payments, unbounded agent actions
  • Compliance certification claims

Proposed refinements PROPOSED

  • Define "weekly active", "accepted message" and "task completed" precisely, and instrument them from Phase 1.
  • Phase 0 demo is two CLI clients and one relay. Build the headless core first, UI later.
  • Keep the data model multi-device and multi-party aware from day one, though groups and sync ship in Phase 3.
  • Run the 15 user interviews during Phase 0, in parallel with the build, so results can change Phase 2 scope.
  • State plainly in every pre-audit release that it has not been independently reviewed.
Day-90 kill / pivot review. Reconsider scope if fewer than 5 pilot groups engage, weekly active use is well below 40%, no design partner will discuss paying, or agent tasks need frequent manual rework. Pivot options: narrow to device-to-device (Connect Link), or to an agent-channel SDK without a chat client.

Business plan

Free private messaging. Paid hosted reliability, enterprise governance and agent connectivity. Funding beyond the 90-day capped pilot depends on retention, reliability and willingness to pay.

Go-to-market sequence PAPER

  1. Bundle with Spike OS and Spike Box for immediate installed-base utility.
  2. Recruit 5–10 design partners from existing enterprise relationships. Sell secure agent workflows, not another chat app.
  3. Publish the SDK and protocol documentation. Encourage independent clients and agents.
  4. Offer managed regional relays and private deployments. Partner with systems integrators.

Unit economics and IP

  • PAPER Gross margin must cover bandwidth, push, storage, support, security, abuse prevention and enterprise deployment.
  • PROPOSED Build a spreadsheet before Phase 4: cost per active user per month, support minutes per account, break-even seats per tier. Model the self-host fraction explicitly, since it caps managed-relay pricing.
  • PAPER Publish specs, SDKs, reference clients and a self-hostable relay under a permissive license. Clear the "Spike Connect" trademark and domain, and review patents, dependencies and export rules before release.
  • OPEN Apache-2.0 is a candidate, not a legal decision. The 90-day budget figure and the product owner are not named in the paper.

Engineering plan

Local-first, end-to-end encrypted, direct P2P when practical, store-and-forward relay when necessary. Established audited primitives only. No promise of anonymity, zero metadata or serverless delivery.

Reference architecture PAPER

Client (desktop / mobile / Spike Box)
  → identity + key management
  → encrypted messaging session
  → direct P2P transport when possible
  → encrypted relay / store-and-forward when necessary

Local encrypted DB holds history.
Cloud: discovery, optional push, availability. Never plaintext.

Threat model PAPER

In scope: compromised devices, malicious relays, impersonation, key substitution, spam, metadata inference, abusive agents. Required mitigations: verified device pairing, key-change warnings, forward secrecy where supported, rotation, recovery design and independent review. Document what relays can see (sender and recipient IDs, timing, size) and what we do not protect.

Agent security model PAPER

  • Each agent has a keypair and scoped credentials with expiry and revocation.
  • Every request is signed. Consequential actions need explicit human approval above a configurable threshold.
  • Rate limits per agent and per scope.
  • Tamper-evident, hash-chained audit log of agent and admin actions. It records actions and metadata, not message content, so E2EE stays intact.
  • Autonomous payments and unbounded actions are out of the MVP.

Work breakdown PROPOSED

Phase 0 · days 0–30

  • Decision records: language, session protocol, transport, storage, license
  • Threat model document
  • Identity: keypairs, device key, safety-number verification
  • 1:1 handshake and encryption, with test vectors and property tests
  • CLI: init, pair, send, recv
  • Demo: two devices exchange verified encrypted messages

Phase 1 · days 31–60

  • Relay: ciphertext only, per-recipient queue, TTL, signed-challenge auth
  • Acks, retry, reconnect, with fault-injection tests
  • Encrypted local database and key storage
  • QR or short-code pairing; chunked encrypted attachments
  • CI: lint, tests, dependency audit, parser fuzzing

Phase 2 · days 61–90

  • Agent envelope, signing, scopes, approvals, receipts
  • Spike OS integration
  • Opt-in, content-free telemetry
  • Security testing pass, pilot onboarding tooling

Phases 3–5

  • Mobile, MLS groups, multi-device sync, backup and recovery
  • Admin console, billing, hosted relays
  • SDK beta, self-host docs, external audit

Quality and operations

  • Threat-model review at every phase gate. No custom primitives; pinned and reviewed dependencies; SBOM.
  • Fuzz and property-test every wire parser and state machine.
  • Independent review scheduled before private beta; external audit before public launch.
  • Incident response and key-recovery drills before Phase 4.
  • Relay observability covers counts, latency, queue depth and errors, never content. Minimal logs with stated retention.
  • Define "within SLO" latency before measuring the 99.9% delivery gate.

Core team PAPER

Product lead 1, protocol and security engineers 2, desktop and mobile engineers 2, backend and relay engineer 1, QA/SRE 1, plus shared design and security review. A staffing model, not a confirmed allocation.
