Message history across multiple devices

How a person with a phone and a laptop sees the same conversations without any server holding their messages. Covers the local message store, device identity, fan-out delivery, history for new devices, and what infrastructure is still needed.

Summary

What we recommend, and what we need you to decide.

Recommendation. Give every person one identity key that signs a list of their devices. Senders encrypt each message separately for every device in that list (fan-out), including the sender's own other devices. Each device keeps history in an encrypted local message store. A new device gets old messages only when an existing device sends it a history bundle during verified linking, or from an optional encrypted backup. A continuous sync log comes later, only if needed.
  • No server holds messages, accounts or history. History lives on your devices.
  • Servers are still needed for offline delivery, key lookup, mobile wake-ups and NAT. They hold only ciphertext and signed public data, and anyone can run one. See the next section.
  • Existing code stays valid. Today's single-device identity becomes a one-device list.

Decisions needed: see Open questions. The main ones are the default history window for new devices, whether contacts must approve a new device, and whether the first release supports backup.

Do we still need a central server?

No central server that manages messages. Yes to some always-on infrastructure.

Pure peer-to-peer cannot deliver to a phone that is off or asleep, and cannot find a peer behind a home router without help. So the design removes the message-managing server, not all servers.

How we avoid a single central operator

  • Home relay in the device list. Each device entry names the relay(s) it reads from. A sender connects to the recipient's relay and delivers there, so no federation protocol is needed and no shared server is required.
  • Replaceable. Changing relay means publishing a new signed device list. Contacts follow it automatically.
  • Self-hosting is first-class. The relay is open source. A Spike Box at home can be your relay, so your messages never touch a third party at all.
What is still visible to a relay operator: who receives how much and when (device IDs, sizes, timing), not content. Choosing your own relay moves that metadata to a party you trust. The current code assumes both people use one relay URL, so the home-relay field is new work (milestone M3).

Design

Five parts: identity and devices, the envelope, fan-out, the message store, and the device list directory.

1. Identity and devices

  • An identity key (Ed25519) represents the person. Its fingerprint is what contacts verify. It never signs messages and is used rarely.
  • Each device has its own Olm account (today's code, unchanged) with its own prekeys.
  • The identity key signs a device list: version number, each device's keys and home relay, and a timestamp. Versions only increase.
  • Where the identity key lives is a real decision (open question 3). Recommended: kept on every device encrypted in the vault, so any device can add or remove devices, with a prompt on the existing device for each change.
DeviceList v7  (signed by identity key)
  identity:  ed25519:9f2c…
  devices:   [ {id: a1b2…, curve25519: …, ed25519: …, relay: wss://home.example, added: v3},
               {id: c3d4…, curve25519: …, ed25519: …, relay: wss://home.example, added: v7} ]
  removed:   [ {id: 77aa…, at: v5} ]

2. Message envelope

Inside the encrypted body (relays never see it):

Envelope { msg_id: random 128-bit,  conv_id,  sender_device,  lamport: u64,
           kind: message | edit | delete | read | sync-control,  body, attachments[] }

The globally unique msg_id makes merging and de-duplication trivial. lamport orders events from different devices without trusting clocks.

3. Fan-out delivery

  • Cost: N recipient devices means N encryptions and N uploads. Fine for two to five devices per person; groups will need MLS later.
  • Receiving device sets the visible state. A device that has not yet fetched a message simply shows it later. Messages are ordered by lamport, then msg_id.
  • Delivery receipts are per device: "delivered to B1" is distinct from "read on B2".
  • New contact devices: before sending, the sender fetches the recipient's device list. If the version changed, the UI shows "Bob added a device" and, for verified contacts, marks the new device unverified until the identity-key signature checks out.

4. Local encrypted message store

Required first (milestone M1), because even single-device history does not exist yet, and attachments need it too.

conversations(conv_id PK, peer_identity, created, retention_days NULL)
messages(msg_id PK, conv_id, sender_device, lamport, ts, kind, body BLOB, state, edited_of NULL, deleted BOOL)
receipts(msg_id, device, kind, ts)                   -- delivered / read, per device
attachments(att_id PK, msg_id, name, size, sha256, state)
sync_cursor(peer_device PK, last_seen_lamport)        -- used by milestone M5
  • Same vault key and AEAD-with-file-name pattern as ADR 0003, applied to a database. Options: encrypt per row, or SQLCipher. Recommendation: SQLCipher, so queries and full-text search work. Open question 5.
  • Insert is idempotent on msg_id, so replays and duplicate deliveries are harmless.
  • Retention is per conversation. Deleting locally is a tombstone, so a sync does not resurrect it.

5. Device list directory

The relay stores each identity's latest signed device list. Clients publish and fetch; the relay only checks the signature chain, not the content.

  • Rollback defense: clients remember the highest version they have seen per contact and refuse lower ones.
  • Hiding a device: a malicious relay can withhold a new device from senders. Mitigations: sender also learns the list from the contact directly during any message (the list version is included in the envelope), and a future transparency log.

Adding a device and getting history

Fan-out delivers new messages. Old messages must be handed over deliberately, because they were never encrypted for the new device.

History bundle

  • Selectable window: last 30 days by default, all, or none ("start fresh"). Per-conversation exclusion. Attachments are optional and off by default (size).
  • Encrypted to N's device key with a fresh random bundle key; split into chunks with per-chunk hashes in a signed manifest. Same chunking design as attachments (shared code).
  • The relay stores the chunks as opaque blobs with a short TTL and a size cap, deleted on completion.
  • Privacy cost: old plaintext now exists on one more device. This is a deliberate trade against forward secrecy of history, so the window defaults to bounded and the choice is shown to the user.

If no existing device is available

A new device cannot get history, only new messages. Optional encrypted backup (milestone M6) covers this and total device loss: a random 256-bit recovery key shown once as words, backup blobs encrypted under it, stored wherever the user chooses (file, own server, relay with a quota). Restore creates a new device, not a clone of the old one.

Keeping devices in step afterwards

Fan-out already keeps incoming and sent messages aligned. Everything else needs a small sync channel.

EventHandled byMerge rule
New message, either directionFan-out (incl. sent copy)Insert by msg_id; duplicates ignored
EditFan-out envelope kind=editHighest (lamport, device_id) wins
Delete for everyoneFan-out kind=deleteTombstone; always wins over edit
Read state, local deletes, settingsSync message to own devices only (kind=sync-control) over the A1-A2 sessionsRead: max lamport. Local delete: tombstone per device group
A device that was offline for weeksIts relay queue (until TTL), then catch-up from another own device using sync_cursorSend all events after the cursor

This reuses the existing channel instead of adding a new protocol: sync traffic is ordinary end-to-end messages between your own devices. A full replicated event log is only needed if catch-up proves too slow.

Open questions

Each changes the build; a recommended answer is given.

  1. Default history window for a new device? Recommend 30 days, with an explicit "all" and "none" choice.
  2. Must contacts approve a new device? Recommend no approval, but a visible notice, and a stronger warning for contacts you have verified.
  3. Where does the identity key live? (a) Copy on every device, encrypted: any device can add or remove devices; one compromised device can add a rogue one. (b) Offline recovery key only: stronger, but users lose the ability to add devices if they lose it. Recommend (a) with confirmation prompts, and (b) as an advanced option.
  4. Is backup in the first multi-device release? Recommend no (M6 later), but say clearly in the UI that losing all devices loses history.
  5. SQLCipher or per-row encryption? Recommend SQLCipher for search and query speed; check its license and build effort.
  6. Relay blob storage for bundles and attachments: separate blob store with its own quota and TTL, or reuse the message queue? Recommend a separate store.
  7. Hosted-relay policy: a relay that accepts delivery from anyone invites spam. Do recipients need to approve unknown senders before a relay queues for them? Affects the business model (Agent Network tier) and abuse handling.
